# The onboard Jetson

## Outcome: it was there, hidden by an address conflict

The Go2 EDU's Jetson **is present and working**. It was unreachable because its
`eth0` was configured as `192.168.123.99` — that is, **the same address the
Unitree manual assigns to the external PC**.

Every symptom followed from that:

* from the PC, `.99` is itself: `arp-scan` skips its own address, so the Jetson
  never showed up in any scan;
* from the Jetson, `ping 192.168.123.161` failed even though ARP resolved: the
  robot replied to `.99` and the replies went to the PC, which won the ARP race
  and discarded them;
* `tcpdump` on the cable showed the robot repeatedly asking
  `who-has 192.168.123.99`, with the PC answering every time.

## Correct addressing

| host | address | notes |
|---|---|---|
| PC | `192.168.123.99/24` | unchanged |
| main board | `192.168.123.161` | MAC `7e:1d:75:60:f5:89`, publishes the DDS |
| **Jetson** | **`192.168.123.18/24`** | MAC `48:b0:2d:f9:15:34` (NVIDIA OUI) |

`.18` is the address the Unitree documentation expects for the onboard computer,
and it was free.

## How it was changed

`eth0` is managed by NetworkManager through the connection **`netplan-eth0`**:
the authoritative configuration lives in netplan, which generates the NM
profile. This is why an `ip addr add` does not stick — it gets reverted.

Immediate change (effective at once, but regenerated by netplan on reboot):

```bash
sudo nmcli con mod netplan-eth0 ipv4.method manual ipv4.addresses 192.168.123.18/24
sudo nmcli con up netplan-eth0
```

Made permanent by editing `/etc/netplan/01-netcfg.yaml`. Original kept at
`01-netcfg.yaml.pre-go2setup`.

## Access

SSH was not enabled from the factory. Enabled from the HDMI console with:

```bash
sudo systemctl enable --now ssh
```

Factory credentials: user `unitree`, password `123` (same for `sudo`).
Factory hostname was `ubuntu`, now `ter-go2-jetson`. Architecture `aarch64`.

From the PC, aliases in `~/.ssh/config`:

```bash
ssh go2jetson        # Wi-Fi
ssh go2jetson-eth    # 192.168.123.18, cable attached
```

Key: `~/.ssh/id_go2_jetson`.

Note that `python3` is 3.8 and the architecture is `aarch64`: Python wheels
without an ARM64 build will not install, and PyTorch needs NVIDIA's Jetson
wheels rather than the ones on PyPI.

## Network topology

PC, main board and Jetson are on the **same layer-2 segment**: both the PC and
the Jetson see `.161` with the same MAC. The robot's external RJ45 port
therefore reaches the same internal bus the Jetson is attached to.

```
PC .99  ---+
           |
      [segment 192.168.123.0/24]
           |
   .161 main board (DDS)      .18 Jetson
```

## Wi-Fi

The Jetson has **no built-in wireless** — interfaces are `lo`, `dummy0`, `eth0`,
`docker0`. Wi-Fi comes from a USB dongle: **TP-Link Archer T3U**
(`2357:012d`, Realtek RTL8812BU).

Kernel 5.10 has no in-tree driver for it (`rtw88` USB support came later), so it
was built from [morrownr/88x2bu-20210702](https://github.com/morrownr/88x2bu-20210702):

```bash
# the Jetson has no internet over eth0, so download on the PC and copy over
scp -r 88x2bu-20210702 go2jetson:~/88x2bu-driver
ssh go2jetson 'cd ~/88x2bu-driver && make -j8 && sudo make install'
echo 88x2bu | sudo tee /etc/modules-load.d/88x2bu.conf
```

Kernel headers, gcc and make were already present. `CONFIG_PLATFORM_AUTODETECT`
in the Makefile handles aarch64 without changes.

Measured on 2.4 GHz (the lab SSID has no 5 GHz): 0% packet loss, 4.9 ms average
round trip, peaks of 45 ms, signal -44 dBm.

Physical connectors on the robot: one USB-C and one USB-A. Note that
`/sys/class/udc/` is empty, so **USB device mode is not available** — a direct
USB cable from the PC to the Jetson is not an option.

## Clock

The RTC is battery-backed and survives power cycles. It was found set to 1970
and was synchronised once; it has held correctly across reboots since.

This matters more than it looks: PC and Jetson need aligned clocks or TF
transforms between the two machines will not resolve.

## What not to do

* **Factory-resetting the robot** acts on the main board, would not have made
  the Jetson appear, and wipes the Wi-Fi configuration.
* **Flashing stock JetPack** would erase the Unitree onboard stack. It would
  need Unitree's own image.

Neither was necessary: the problem was a duplicate IP address.
